4. Iterable та iterator

Iterable – об'єкт, з якого iter() отримує iterator; iterator зберігає стан обходу, віддає елементи через __next__() і завершується StopIteration. Цикл for викликає iter(), потім next() до StopIteration. Власний iterator Batcher віддає пакети студентів; він one-shot (iter(b) is b). JournalSource – окремий iterable: кожен iter() створює новий генератор файлів, тому його можна обходити повторно.

class Batcher(Generic[T]):
    def __init__(self, items: Iterable[T], size: int) -> None:
        if size < 1:
            raise ValueError("Розмір пакета має бути >= 1")
        self._iterator = iter(items)
        self._size = size

    def __iter__(self) -> "Batcher[T]":
        return self

    def __next__(self) -> list[T]:
        batch = list(islice(self._iterator, self._size))
        if not batch:
            raise StopIteration
        return batch

class JournalSource:
    def __init__(self, root: Path) -> None:
        self.root = root

    def __iter__(self) -> Iterator[Path]:
        return iter_csv_files(self.root)

5. Генератори, yield і yield from

Streaming reader і рекурсивний пошук файлів використовують yield from; файл відкритий, доки генератор не вичерпано або не закрито:

def read_lines(path: Path) -> Iterator[str]:
    with path.open("r", encoding="utf-8-sig", newline="") as file:
        yield from file

def iter_csv_files(root: Path) -> Iterator[Path]:
    for entry in sorted(root.iterdir()):
        if entry.is_dir():
            yield from iter_csv_files(entry)
        elif entry.suffix == ".csv":
            yield entry

Transformation stage – generator function з yield: кожен студент отримує поле level (рівень успішності) лише тоді, коли його запитує наступний етап. Етап не має власного стану, тому пам'ять не залежить від кількості студентів:

def grade_level(grade: float) -> str:
    return next(label for threshold, label in GRADE_LEVELS if grade >= threshold)

def enrich_students(students: Iterable[Student]) -> Iterator[StudentRecord]:
    for student in students:
        yield StudentRecord(*student, level=grade_level(student.average_grade))

Generator expressions використано у build_pipeline (read_rows(path) for path in files), find_first, first_n_students, top_students і running_average.

Рисунок 1 – Схема потокового конвеєра

Функція build_pipeline лише з'єднує генератори – жоден рядок не читається, доки результат не почне споживати sink:

def build_pipeline(
    paths: Path | Iterable[Path],
    *,
    group: str | None = None,
    min_grade: float | None = None,
    errors: Counter[str] | None = None,
    stages: Counter[str] | None = None,
) -> Iterator[StudentRecord]:
    files = [paths] if isinstance(paths, Path) else paths
    rows = chain.from_iterable(read_rows(path, stages) for path in files)
    students = log_stage("4 validate", validate_students(rows, errors), stages)
    if group is not None:
        students = log_stage("5 filter group", filter_by_group(students, group), stages)
    if min_grade is not None:
        students = log_stage("6 filter grade", filter_by_min_grade(students, min_grade), stages)
    return iter(log_stage("7 transform", enrich_students(students), stages))

Validation, filtering, топ-N, streaming aggregation і динамічні пакети. nlargest тримає в пам'яті лише N кандидатів, а не весь потік:

def validate_students(
    rows: Iterable[dict[str, str]],
    errors: Counter[str] | None = None,
) -> Iterator[Student]:
    for row in rows:
        result = parse_student(row)
        if isinstance(result, str):
            if errors is not None:
                errors[result] += 1
            continue
        yield result

def filter_by_min_grade(students: Iterable[Student], minimum: float) -> Iterator[Student]:
    for student in students:
        if student.average_grade >= minimum:
            yield student

def top_students(
    records: Iterable[StudentRecord],
    n: int,
    predicate: Callable[[StudentRecord], bool] | None = None,
) -> list[StudentRecord]:
    candidates = records if predicate is None else (r for r in records if predicate(r))
    return nlargest(n, candidates, key=attrgetter("average_grade"))

def streaming_average(values: Iterable[float]) -> float:
    total = 0.0
    count = 0
    for value in values:
        total += value
        count += 1
    if count == 0:
        return 0.0
    return round(total / count, 2)

def running_average(records: Iterable[StudentRecord]) -> Iterator[float]:
    grades = (record.average_grade for record in records)
    return (round(total / n, 2) for n, total in enumerate(accumulate(grades), 1))

def batched_by_group(
    records: Iterable[StudentRecord],
    max_size: int = 100,
) -> Iterator[list[StudentRecord]]:
    for _, members in groupby(records, key=attrgetter("group")):
        yield from Batcher(members, max_size)

8. Eager і lazy: експеримент

Eager-версія повністю матеріалізує кожен етап у list; lazy-версія – це build_pipeline. Обидві використовують ту саму функцію перевірки parse_student і дають однаковий Summary (перевіряється assert). Час – найкращий із 2–3 запусків без tracemalloc, пам'ять – пік tracemalloc в окремому запуску, sink – summarize.

def eager_process(path: Path) -> list[StudentRecord]:
    lines = path.read_text(encoding="utf-8-sig").splitlines()
    cleaned = [line.strip() for line in lines if line.strip() and not line.startswith("#")]
    rows = list(csv.DictReader(cleaned))
    parsed = [parse_student(row) for row in rows]
    students = [item for item in parsed if isinstance(item, Student)]
    return [StudentRecord(*s, level=grade_level(s.average_grade)) for s in students]

Аналіз. Пікова пам'ять eager росте лінійно з кількістю записів (8.3 → 415.1 МБ), а lazy залишається ≈0.07 МБ (буфер читання, поточний запис і лічильники) – у 5 563 рази менше на 500 000 записів. За загальним часом на 10 000 записів lazy повільніший (lazy/eager = 1.14), на 500 000 записів – швидший (lazy/eager = 0.79): обидві версії виконують ту саму обчислювальну роботу, тож різниця в часі невелика; найімовірніше, її дають виділення й звільнення пам'яті під проміжні списки в eager-версії. Тому висновок «generator завжди швидший» неправильний: його головні переваги – пам'ять і перший результат, який lazy-конвеєр дає за 0.16 мс проти 2.11 с. Early termination на 1 000 000 записах знаходить збіг на позиції 651, прочитавши лише початок файла, – у 1 325 разів швидше і з 75 КБ пам'яті замість 831 МБ.

Недоліки lazy-підходу: конвеєр one-shot (для другого проходу його треба створити заново), немає len() та індексації, помилки даних виникають під час споживання, а файл залишається відкритим, доки генератор не завершено. Eager доцільний для невеликих наборів із повторним доступом і сортуванням; lazy – для великих файлів, потоків і пошуку з ранньою зупинкою.

Побудовано потоковий конвеєр обробки журналу студентів (варіант 1), у якому кожен запис проходить етапи читання, очищення, parsing, validation, filtering, transformation і aggregation лише тоді, коли його запитує споживач. Експеримент показав, що lazy-обробка тримає пам'ять сталою і дає перший результат майже миттєво, тоді як eager потребує пам'яті, пропорційної розміру файла; за загальним часом різниця невелика й залежить від обсягу даних. Тож вибір між eager і lazy залежить від обсягу даних і способу їх використання.
